# S5-R3: legacy import repairs (S5 review Y5 and Y6)

Branch `fa/s5-r3`, from `96be105d0`. Repairs findings **Y5** and **Y6** in
`reviews/S5-review.md` for S20-legacy-import (FA-54). Nothing was pushed,
deployed or run against a hosted project. `lib/db/types.ts` is unchanged: no
signature changed, so the committed types still fit.

## What was built

### Y5: an amenity-staged import always reaches a review queue

- **Script** (`scripts/import/legacy-import.ts`, `readCandidates`): an
  amenity check is offered as a label candidate only when its question is on
  the venue's working list (`knowledge_working_list`, `disabled_at is null`,
  the rule `private.knowledge_in_scope` reads). An off-list check is neither
  matched nor counted towards an "ambiguous" match against a dish or place
  with the same name.
- **`public.legacy_import_complete`**: the amenity branch also requires
  `private.knowledge_in_scope(...)`. An off-list amenity is not staged; the
  photo takes the existing fallback (unlabelled, note "Imported. Legacy
  label: …").
- **`private.asset_unlabelled_reason`**: an amenity-staged import is held out
  of Needs label only while its check is active and in scope, the same checks
  `private.amenity_photo_rows` lists. When the question leaves the working
  list or the check is archived, the photo appears in Needs label as
  **Imported, no slot matched**; when it comes back, the photo returns to the
  amenity queue. Decided photos stay out of Needs label as before
  (`amenity_photo_decisions`).

### Y6: a failed line is retried after the 24-hour cleanup

- **`public.legacy_import_reserve`**: a tombstoned row of the batch raises
  `import_reservation_closed` (55000) instead of being returned as
  reusable. A live, not-ready row it reuses is touched (`updated_at`) so a
  cleanup pass cannot tombstone it while this run finishes it.
- **Script** (`importOne`): `importAssetId(batch, line, attempt)`; attempt 0
  is the id earlier runs used (unchanged). The script reads attempts 0 to 19
  in one query and uses the first that is not tombstoned. A fresh attempt
  stores the original before reserving, as on a first run. After 20 expired
  attempts the line fails with a message to use a new manifest.
- **Idempotent**: a done line is still reported `unchanged` from
  `media_import_items` (keyed by batch and line, not asset id), and a rerun
  finds the same live attempt.

## Decisions (owner asleep; recorded here)

1. **Y6: a new attempt id, not reviving the tombstoned row** (the review
   offered either). Reviving is unsafe here: a cleanup run may have listed
   the row's objects and remove a freshly stored original after the revive;
   and the storage write guard (`private.guard_media_original_write`) refuses
   an original written to a key owned by a reservation that is closed or held
   by a non-staff (admin) uploader, which is how most imports are held. A new
   id derived from batch, line and attempt keeps reruns deterministic and
   needs no change to the guard or to cleanup.
2. **Y6: `reserve` refuses rather than revives** a tombstoned row, so no
   caller can finish against a dead row.
3. **Y5: in scope means the working list**, matching `amenity_photo_rows`
   (FA-32's working-list rule). An off-list match is treated as no match (kept
   as note), not as an error.
4. **Y5: Needs label reason stays `imported`** ("Imported, no slot matched")
   for an import whose staged amenity left the working list. That is
   accurate (no slot in a queue matches it now) and needs no new status word.
5. **Open-upload limit** (review note on Y6): a failed reservation held by a
   staff contributor still counts until the next run finishes it or cleanup
   tombstones it (24 h), as before. Not changed: it is bounded and the rerun
   now clears it.
