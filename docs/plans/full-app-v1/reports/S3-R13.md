## Decisions to record (the coordinator's call)

1. **R13-1. Fix label withdraws the old decision in the same step.** A correction of a decided staff label needs a reason. That reason is recorded on the withdrawal and on the new acceptance. A label already corrected by a live reviewer row still refuses (`menu_item_relinked`): withdraw that correction first. Two live corrections of one label are never allowed.
2. **R13-2. Fix label accepts for the target**, as the dish Fix label always has: at the public level, or the picker's level for place and amenity calls (the UI sends public). Fix label still always accepts; the review records this as a known gap, unchanged.
3. **R13-3. The source is ended with the decision functions.** An accepted place or amenity photo is withdrawn. A waiting or asked-again one is set to Not used, with the reason. A Not used or withdrawn one is left as it is. A place label is then closed (`removed_by` = the reviewer).
4. **R13-4. A place label made by Fix label is credited to the uploader.** `added_by` is the uploader, because area credit and the coverage rule read `added_by = uploader`. `fixed_by` holds the reviewer, and `fixes_label_id` the label it replaced. This matches dish corrections, whose `author_id` stays the uploader.
5. **R13-5. A dish label still waiting, moved to a place or amenity.** The insert guard makes every row start live, so a `staff_label` row is inserted accepted and withdrawn at once. One `withdrawn` event is recorded, and no `accepted` event. The label then leaves the queue the way a decided one does (`wd.hit`).
6. **R13-6. Place or amenity to dish uses `assign_menu_item_photo`'s unlabelled path.** The transaction-local setting `nabalens.fix_label_asset` lets through a photo that is not tagged food or drink. PostgREST clients cannot set it. A direct `assign_menu_item_photo` call still refuses such a photo, and a security test proves it.
7. **R13-7. Dish to dish stays the relink path** (`decideMenuPhotoAction`), and a Needs label photo to a dish stays `assign_unlabelled`. `review_fix_label` refuses both with `invalid_input`, so each move has a single path.
8. **R13-8. `review_fix_label` refuses the uploader unless the venue is single-reviewer (K6), admins included.** This is the rule place and amenity decisions already use.
9. **R13-9. Staff are told only about dish corrections.** "Label corrected" is a dish-only notification (FA-7, `notify_on_label_corrected`), so a place or amenity Fix label notifies no one. The help text says "For a menu item, the contributor is told." Telling staff about place and amenity fixes is a candidate for the next batch.
10. **R13-10. Needs label reads at most 20 queue pages (480 photos)**, then says that more wait.
11. **R13-11. On a decided review card, Fix label sits behind More actions with Withdraw.** This keeps the card's main row unchanged.

No new rows in `departures.md` or `catalogue.md`. The picker is the listed ItemPickerDialog, extended with the SegmentedControl primitive.
