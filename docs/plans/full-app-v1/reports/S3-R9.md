### W5 / D4: how a question joins the working list

Confirmed on HEAD, as the review describes:

- `amenity_add_checks` (latest body 20261107150000) never touched the
  working list.
- `private.venue_template_rows` skipped any question already active at the
  venue, so the template could not fix it later.
- No screen calls `knowledge_set_working_list`.

**Product rule chosen** (`20261118127000_working_list_on_add.sql`). The
review's first option, limited so the B01 access rule still holds:

1. **Add check.** `amenity_add_checks` puts each key it adds, restores or
   finds active on the venue's working list when two things hold:
   - the venue already has an **open** working list, meaning an admin
     brought it onto the knowledge layer, normally with the venue template;
   - the question has a knowledge rule. Every question has one since 20261118121200.

   The row's `enabled_by` is the person who added the check, with the reason
   "Added as a check at this venue". It writes a `working_list_enabled`
   knowledge event. A key an admin took off this venue's list (a closed row)
   stays off.

   A venue with no open list keeps the legacy path exactly as before. So
   "an admin enables a venue's working list" (`docs/knowledge/access-and-rights.md`)
   still holds: a manager only extends a list an admin opened. The new
   helper `private.knowledge_working_list_join` is not callable by any API
   role.

2. **Template.** `private.venue_template_rows` now also offers a question
   whose check is active but has **never** been on the venue's list: a core
   check from `amenity_enable_venue`, or one a manager added before the venue
   had a list. `admin_venue_apply_template` (unchanged) then puts it on the
   list. It leaves the check and its answers alone. A question with any list
   row, open or closed by an admin, is still left out.

**Legacy submit (`knowledge_path_required`).** A check on the list is
answered through `knowledge_submit`. The staff capture page already picks the
knowledge form when `inScope` is true
(`app/staff/tasks/amenities/_capture/screen.tsx`), so no app change is
needed. Venues without a list keep `amenity_submit_finding`.

**Why not join every added check, or core checks at `amenity_enable_venue`?**
That would move every venue onto the knowledge path without an admin
opting in. It would also break the legacy amenities journeys and about 20
security tests that rely on the legacy path being unchanged off the list
(b01-design "Outside the working list, behaviour is unchanged").

### e2e: amenities "Wi-Fi needs a photo, a video and the redaction tick"

**Not a product defect.** The rule changed on purpose:

- FA-32: "policy questions (dogs, Wi-Fi) need the fact only".
- FA-47 / S2-INT, `20261118109300_int_policy_evidence.sql`: catalogue
  version 2 sets `guest_wifi`'s evidence rule to `none`, and
  `private.amenity_rule_met('none', …)` is true.

So "photo only, with the tick" is now a valid Yes, and the spec's first
refusal recorded a submission (`expectSubmitRefused`, helper line 573).

That migration keeps two Wi-Fi rules: a Yes needs the test notes
(`invalid_wifi_metadata`) and the redaction tick (`redaction_not_confirmed`).
The spec is renamed "Wi-Fi needs the test notes and the redaction tick, not a
photo or video, and records the test notes internally". It now checks:

- In the UI, a photo and a video without the tick are refused.
- Through the RPC, a Yes with no media and no tick gets
  `redaction_not_confirmed`, not `evidence_rule_unmet`.
- Photo and video without the tick get `redaction_not_confirmed`.
- Missing notes get `invalid_wifi_metadata`.
- A photo alone, with the notes and the tick, is Complete, and the photo is
  kept with the answer.
- The manager still sees the internal notes.

## Decisions for the coordinator to record

1. **W5 working-list rule.** A check added or restored at a venue with an
   open working list joins it, if its question has a knowledge rule and an
   admin has not taken it off that venue's list. A venue with no open list
   stays on the legacy path. Only an admin opens a venue's list, normally
   with the venue template.
2. **Template.** The venue template also brings an active check that was
   never on the venue's list onto it, without copying or changing an answer.
3. **Wi-Fi spec.** Wi-Fi needs no media (FA-32 / FA-47). The e2e spec was
   updated to match; the product was not changed.
