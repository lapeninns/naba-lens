## X3: the template and a check added before the list

`private.venue_template_rows` (latest body 20261118127000) only admitted a
question through `(no source and is_core) or active at the source`. The
S3-R9 clause for "active but never on the list" sat behind that filter. So a
non-core check (pool table) a manager added on the legacy path was never
offered by the group catalogue. The picker blocks re-adding an active check,
so the check never joined the list.

`20261118132000_template_offers_unlisted_checks.sql` adds a third way in: a
check that is active at the target venue and has no working-list row at all.
A question with any row (open, or closed by an admin) is still left out, so an
admin's choice to take it off stands. `admin_venue_apply_template` is
unchanged. It lists the key and leaves the check and its answers alone. I
chose the review's first option (template offers it) over a backfill on first
open. It keeps one product path (preview shows what apply does), and the admin
sees the check in the preview before applying.

## X10: why a package photo is stale

`20261118132100_export_item_stale_reason.sql`:

- `private.export_item_stale_reason(...)` (no API role may call it) reads the
  conditions of `export_candidate_rows` (latest 20261118116000) in order. It
  names the first that fails: `deleted`, `withdrawn` (Library withdrawal, use
  withdrawn, public use withdrawn, or the reviewer withdrew the decision the
  item was exported under), `off_menu`, `subject_retired` (place retired,
  facility archived or off the list), `label_changed`, `check_due`,
  `fact_changed`, `review_changed`, or `changed` when none can be named (an
  invalidated package whose item has since become eligible again).
- `public.export_package_detail` (body from 20261118108500, latest) adds
  `staleReason` per ineligible item. Eligibility, invalidation and downloads
  still follow `export_package_stale` unchanged.

App: `STALE_REASONS` / `StaleReason` in `lib/server/exports/model.ts`, parsed
into `ExportPackageItem.staleReason`. `staleChip(reason)` in
`app/admin/publishing/_components/copy.ts` maps to `package_item_<reason>`
chips (new in `status-chip.tsx`, tone negative, warn square). The override
`<StatusChip state="package_invalidated">Withdrawn since</StatusChip>` is gone.
The page's other wording follows suit. "Every photo in it was withdrawn" is
now "No photo in it can be downloaded now", and the button is now "Rebuild
without those photos" (it was "Rebuild without withdrawn photos"). The AC32
e2e spec is updated to the new button name.
`PUBLICATION_WORDS` restated the `publication_*` chips and was used only in a
test, so it is removed; the test reads the chips.
