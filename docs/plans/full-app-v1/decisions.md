# Full App v1: decisions and assumptions

The owner asked (18 Nov 2026) for the whole [Full App Specification](../../spec/NabaLens-Full-App-Specification-v1.0.md) to be built autonomously, choosing the recommended option for routine decisions and recording it. Each decision below says what was chosen, why, and what would reverse it. "Spec §" points at the specification; "D8", "D9" and "DESIGN.md" at [the Album design system](../../design-system/DESIGN.md).

Owner review is wanted on the ones marked **review**.

## How conflicts with earlier owner decisions are resolved

The gap map found 32 places where the spec and an earlier owner decision differ. The rule used: keep the earlier owner decision where the spec's acceptance check can still be met, and follow the spec where the difference is about access, data safety or accuracy.

## Access and data safety: spec followed

| ID    | Decision                                                                                                                                                                                                                                        | Why                                                                                                                                                                                 |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FA-20 | **review** Staff see colleagues' photos only once accepted (public or reference). Unreviewed colleague media is not shown in the Photos feed or on Album tiles; a slot shows "1 waiting" instead. Own photos are always visible to their owner. | Spec §3.3 row 3 ("View another person's unreviewed media: No"). This reverses Goals v0.5's "review never gates visibility" for staff; managers still see everything at their venue. |
| FA-21 | Staff can withdraw their own unreviewed upload. They cannot permanently delete an accepted original; they can ask for it to be removed, and an admin decides with a reason and an impact preview.                                               | Spec §3.3, §16; the critic found staff could delete accepted originals.                                                                                                             |
| FA-22 | Per-venue roles: a person can be staff at one venue and manager at another (AC14). Implemented as a `venue_memberships` model that the existing manager grants and profile venue feed.                                                          | Spec §3.1, AC14, AC40.                                                                                                                                                              |
| FA-23 | Admin accounts must use MFA (TOTP through Supabase Auth); managers can turn it on.                                                                                                                                                              | Spec §3.2.                                                                                                                                                                          |
| FA-24 | Colleague media streams send renditions without location metadata; originals stay with managers and admins.                                                                                                                                     | Spec §12.3, critic finding.                                                                                                                                                         |

## Model choices

| ID    | Decision                                                                                                                                                                                                                            | Why                                                                   |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| FA-30 | No rebuild of the existing per-kind tables (menu photos, area photos, amenity checks, knowledge). A single coverage function computes every slot's state from them, and staff Album, manager and admin counts all read it.          | Keeps working data and history; one rule satisfies AC39.              |
| FA-31 | Each review decision has a level: **public** (closes a public-photo requirement) or **reference** (kept, does not close it).                                                                                                        | Spec §2, invariant 4, AC16.                                           |
| FA-32 | Amenity questions have a photo requirement separate from the fact. A confirmed No needs no photo; a confirmed Yes still needs a reviewed photo where the catalogue asks for one; policy questions (dogs, Wi-Fi) need the fact only. | Spec §2, §4.2, AC24, AC25.                                            |
| FA-33 | One organisation (Lapen Inns) is implicit. Venues gain timezone (default Europe/London) and operating status; no organisation table until a second customer exists.                                                                 | Spec §11 allows derived ownership; avoids a migration of every table. |
| FA-34 | Monthly personal targets (Goals v0.5) stay; they are not a leaderboard and no ranking is shown.                                                                                                                                     | Spec §18 forbids leaderboards, not personal targets.                  |
| FA-35 | Exact duplicates are detected by a SHA-256 of the original computed at finalisation; a duplicate never adds coverage or contribution credit.                                                                                        | Spec §12.4, AC21.                                                     |
