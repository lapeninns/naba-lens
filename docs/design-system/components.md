# Component values: spec and shipped

Companion to [common-room.md](common-room.md) §4. One table per component: what the spec sets, what the product ships today, and whether they agree. Taken on 14 Nov 2026 by reading the prototype stylesheets and the shipped components, then re-checked line by line by a second reader. Nothing was rendered in a browser, so "Shipped" is what the code says, not a measurement of the screen.

**How to read it**

- **Spec** is the value Common Room v0.3 sets. The bracket after it says where it was read: `cr:412` is line 412 of the prototype's `common-room.css`, `pr:` is `pass-rail.css`, `ui:` or `ui.js:` is the prototype's builder script, `CONTRACT:` is its builder contract, and `D§4` is `common-room.md` section 4. The prototype files are outside the repo and superseded (see `common-room.md` §13); the references are provenance only. Where the two stylesheets disagreed, the later one (`common-room.css`) wins and is the value shown.
- **Shipped** is what the repo does, with a path and line. Line numbers drift; the path is the lasting part.
- **Same?** is yes, partly or no. A "no" or "partly" is either recorded in [departures.md](departures.md) or is work for the roadmap in [strategy.md](strategy.md).
- "not specified" means the spec is silent.

When a component changes, change its table in the same pull request.

**Path check (18 Nov 2026, S3-R7).** Every repo path below was checked against the tracked tree. Files deleted after the snapshot are marked _(deleted since this snapshot)_ with what replaced them; line numbers were not re-taken. `common-room.css`, `pass-rail.css`, `CONTRACT.md` and `ui.js` are the prototype files outside the repo, cited for provenance only.

### Differences to know: actions

- Danger now matches the spec default: `danger` is transparent with a 1.5px warn edge and takes warn-bg on hover. `danger-quiet` is the same without the edge. The spec's `.danger.solid` (warn-bg fill, no edge) is not built: the six variant names have none for it.
- Default kind matches: a bare `<Button>` is the grey secondary, and primary is asked for by name (components/ui/button.tsx).
- pass-rail.css values that lose to common-room.css and must not be copied: control radius 12px (now 8px), card radius 16px (now 12px), secondary and ghost 1px borders (now none), danger 1px border (now an inset 1.5px edge), disabled opacity .55 (now a grey fill with an inset edge), button row gap 10px (now 8px), plain icon button with no fill and a surface-2 hover (now surface-2 fill, raised hover), labelled icon button weight 500 (now 600), segmented radius 14px/10px and 48px segments (now full radius, 44px), select pill 48px with a 1.5px border and fg fill when pressed (now 44px, no border, accent-soft). Still taken from pass-rail.css because common-room.css does not restate them: button gap 10px, the 150ms/100ms transition, the 1px pressed move, `.full`, and the `button` reset (no border, no background).
- There is no shared icon button. The spec's round 48px grey disc, the labelled form and the stacked form (icon over a word, min width 64px) do not exist as components; icon-only buttons use Button's `icon` size, which is 44px with an 8px radius, not a 48px round disc. No stacked icon button was found in components or app.
- Two segmented controls ship with different semantics and looks: ToggleGroup/Toggle (`aria-pressed`, 8px default gap, drop shadow on the selected segment) and app/_media/segmented.tsx _(deleted since this snapshot)_ (native radio group, 4px gap, inset edge only, no hover fill). The spec defines one, with `aria-pressed` or `aria-current`.
- ToggleGroup only draws the grey track and its 4px padding when the group is given `variant="default"` (it has no default for that prop). The only production use, components/nabalens/library-filters.tsx:341 and 484, does not pass it, so as written those segments sit on no track. Check this in the browser before treating ToggleGroup as the reference segmented control.
- The select pill style is duplicated as string constants in five files, under two names (`PILL` in two, `SEGMENT` in three), with 16px versus 14px padding and `aria-current="page"` versus `aria-pressed`. The `SEGMENT` constants are select pills, not segments. The shared `Toggle` outline variant is not used outside the dev preview. review-filters.tsx:23 also has a `CHIP` constant, a removable current pill that the spec does not define.
- Stepper: the spec asks for one shared `.stepper` with a mono 19px value in an 88px field and drawn bars of equal weight; the shipped one lives in a feature file, sets the value in the body face at 18px bold in a field about 68px wide, uses icon-font glyphs, and marks a changed value in accent-text rather than fg. It also uses native `disabled`, where common-room.md §7 asks for `aria-disabled` and a stated reason.
- The spec CSS itself is not yet one stepper: the drawn glyph (`.a-manage-pm`, cr:1090-1091) and the changed state (`.a-manager-account-stepper .num-in.changed`, cr:1102) exist only on area classes, and the area copies use `.num-in` at 18px mono (cr:401) where `.stepper .input` is 19px (cr:227). The comment at cr:223 says both area copies should switch to `.stepper`. The flattened spec should state which values the shared stepper takes.
- Not in the spec CSS but shipped: `aria-invalid` edge on buttons and toggles, the secondary and quiet pressed fill, the `aria-pressed` toggle look, two icon sizes on Button (`icon`, `icon-lg`), a `link` variant inside Button (the spec has a separate `.link` class), and a tick on the current filter pill. The spec gives no icon size for buttons beyond the builder's 24px default; shipped buttons use 22px.

### Differences to know: forms

- There is no shared Textarea, Checkbox, Radio row or Tile check in components/ui. Each is a feature-local class string or native control, and the copies disagree on height, padding, edge width and text size (for example textarea minimum height is 112px, 96px and 56px against the spec's 120px). There are five textarea class sites: reason-dialog.tsx, team-roster.tsx:1070 (an inline copy), menu-document-editor.tsx, field-styles.ts and requirement-setup.tsx:635 (64px override).
- Counts today: rg 'type="(checkbox|radio)"' app components finds 11 checkbox and 9 radio inputs. Two of the radios (components/nabalens/invite-staff-dialog.tsx:127 and app/_media/segmented.tsx:52 _(deleted since this snapshot)_) are visually hidden inputs behind a segmented control, not radio rows. rg "has-checked:shadow" components finds three photo-select tiles.
- The spec draws its own 28px checkbox and radio marks over a visually hidden input. The repo uses visible native inputs tinted with accent-color at 24px, and at 20px or 16px in the amenities files, some using accent or primary rather than select.
- The spec contradicts itself on a selected row: common-room.css line 430 gives a card shadow plus a 2px inset select edge, while common-room.md section 2 (and the section 9 change list) says a selected row uses accent-soft. Shipped radio rows use accent-soft only; FieldLabel in components/ui/field.tsx applies both.
- Tile check differs in kind: the spec is a button with aria-pressed, a 3px ring outside the photo and the words Select or Selected. The repo is a label with a native checkbox, a 3px inset ring on the whole tile and an accent-soft fill. Spec ineligible tiles have no control and a dimmed photo; shipped ones keep a disabled checkbox and do not dim the photo. The three shipped tile grids also disagree on columns (3 to 6, 2 to 4, 3 to 5).
- Code entry: the spec carries two type rules for the one input (.a-gi-code 700 24px with 0.3em spacing, .a-states-code 22px with 0.2em spacing) and still holds the older six-box .code-boxes CSS. The comment above .a-states-code (common-room.css line 993) names sign-in-code-step.tsx. The repo ships 18px, weight 400, 0.2em spacing. The flattened document needs to pick one.
- Disabled: common-room.md section 7 asks for aria-disabled, the control kept in the focus order and the reason shown beside it, and the CSS gives fields no disabled style. The repo uses the native disabled attribute, which takes the control out of the focus order, with ink-muted text and a 1px line edge.
- Select and Switch exist in the repo but not in the spec. The spec's select-style control is a full-width button.input that opens a sheet or dialog; the shipped Select is a Base UI listbox popup that fits its content by default and is made full width by its only wrapper, option-select.tsx. The Switch has no spec source at all; it has one size, with a 64 by 44px hit area.
- Smaller gaps in the shared Input: height is fixed at 56px where the spec sets a minimum, line height is 1.375 against the inherited 1.5, and there is no leading-icon slot (.input-wrap in the spec: 24px icon at left 14px, input left padding 48px). The spec also has a 44px square sign-in check (.a-states-check-input, 4px radius, common-room.css lines 997-1001) with no shared equivalent in the repo.
- Several spec values are not in the two CSS files or CONTRACT.md but in the kit builder, assets/ui.js (icon sizes, role="alert" on the error, aria-hidden marks, aria-pressed, the words Select, Selected and Choose…). They are cited as ui.js:line; pr: means pass-rail.css. Inherited text values come from .app (common-room.css line 137: 400 17px / 1.5 body) and the form reset (pass-rail.css line 61: font inherit).

### Differences to know: states

- Chips on photos: the spec restyles .chip on a photo (plate fill, light Ready and Submitted colours, cr:518-520). The repo has no such StatusChip variant; photos use a separate TileBadge (components/nabalens/media-tile.tsx:32-45) that is 28px high with a 16px icon, 4px radius and no wrap, so it is below the 32px chip height and is not one of the §3 shapes.
- Ready and In progress have shapes in CHIP_SHAPES but no CHIP_STATES entry. Nothing draws the ready shape. The progress shape is used once, as an override: RequirementStatusBadge draws an active requirement as the In progress pill with the word "Active" and no icon (components/nabalens/coverage/coverage-badges.tsx:63; word from components/nabalens/coverage/copy.ts:60). The word "Ready" only exists in UPLOAD_STATE_LABEL (components/nabalens/format.ts:62), where it is a technical upload state, not the §3 Ready chip.
- Grant states use different words from the spec: §3 says "In effect" and "Not in effect: reason"; the code says "Venue manager", "Revoked by an admin", "Ended: moved to another venue" and "Ended: account deactivated". The shapes match (neutral outline square, grey square).
- Menu changed: the shipped word is "Menu changed — review coverage" with an em dash; the spec chip word is "Menu changed" and the prototype's coverage data uses "Menu changed: review coverage" with a colon (ui.js:562). The prototype data also conflicts with §3's reserved shapes: it draws coverage 'none' with the setup chip, 'changed' with the overdue chip and 'current' with the accepted chip (ui.js:560-563). The repo uses plain pills for none and current and the changed shape for changed, and so follows §3.
- The spec draws Menu changed three ways: .chip.changed with fg text (cr:267), .chip.a-manage-changed with warn-fg text (cr:1067) and .chip.a-admin-tag.changed with a surface-2 fill and an inset 4px bar (cr:1244). The repo ships only the first. The admin tag's surface fill (cr:1241) also has no shipped shape.
- Upload words: the spec draws them as .q-state, a mono 17px/600 word with an 18px icon and no box (cr:492-495), with Uploaded in ok-fg. §3 lists Waiting, Uploading 42%, Processing, Uploaded, Failed, Cancelled; CHIP_STATES adds "Ready to upload" and has no "Uploaded"; the shipped upload shapes sit on the chip base, so they keep the 32px min height and may wrap. The upload dialog's headline words are Saved, Saving… and Needs attention, with the §3 words only as detail lines.
- Icons: the spec's `setup` icon is eight short rays (ui.js:23); the repo uses a spanner (Wrench) for Needs setup and Needs verification. The spec's `minus` is a minus in a circle (ui.js:41); the repo matches it for Not applicable (MinusCircle) but uses a plain Minus for Not present. Processing is an hourglass in the spec (ui.js:376) and a clock in CHIP_STATES. D§4 says a chip is always icon + word, but a shipped chip given only a tone, an unknown key or an overriding tone or shape has no icon.
- Shipped additions with no spec drawing: the warnSquare shape (the default for tone 'negative'), the states read_only and needs_labels, the strike-through on Discarded, and the neutral (ink) CountBadge. TONE_SHAPE also lets a tone-only chip take the 'met', 'overdue', 'waiting' or 'closed' shapes with any word, and the shape prop can select a reserved shape; only a code comment guards the §3 reserved-shape rule. The tone stored in CHIP_STATES does not always match the drawn colour (Self-review is 'attention' but drawn in info; Present is 'neutral' but drawn in ok); tone only reaches the page as the data-tone attribute when a state has its own shape.
- The count badge is one 26px disc in code; the spec has two sizes (tab 28 × 26 including a 2px surface border, side nav 30 × 28 pushed to the right edge). The shipped phone tabs put a 2px ring outside the disc, so the badge is 30px overall there. No side nav badge was found: on desktop the badge sits inline after the label in the top-bar nav (components/nabalens/app-shell.tsx:218-223).
- Words for the same idea are spread across files and do not always agree: "Asked for another" and "Asked for another photo" (review-copy.ts) against the registry's "Needs another photo"; "Waiting" means a queued upload in CHIP_STATES and a photo awaiting review in review-copy.ts; "Active" means an account in CHIP_STATES and an in-progress requirement in coverage/copy.ts; "Complete" and "Not applicable" are defined again in lib/amenities/contract.ts, and Submitted, Accepted, Needs another photo, Needs setup and Retired again in components/nabalens/coverage/copy.ts.

### Differences to know: containers and messages

- The share box is retired. ### Differences to know: photos, progress and uploads

- The merge-above-12 rule exists only in code: common-room.md, CONTRACT.md and both CSS files say one segment per photo with no upper limit. The flattened spec must either adopt the rule (three shipped copies agree on > 12) or mark it as a code-only extension.
- Segmented progress ships three times with small drifts: ProgressSegments (shared, mono 17px label, optional key; used by one product screen, components/nabalens/menu-photos/our-menu-screen.tsx, plus the dev preview), Frames in coverage/layout.tsx (46px count, flex row with a 64px segment cap, 8px compact, sr-only text) and PhotoSegments in tasks/month-card.tsx (no words of its own). The spec's admin table variant is 16px tall; Frames compact is 8px.
- Plain bar default matches: Progress fills ink by default and ok-fg only with tone="ok", which the bars that count accepted work pass.
- Upload queue wording differs: the spec lists six mono states (Waiting, Uploading 42%, Processing, Uploaded, Failed, Cancelled); the shipped row shows three words (Saving…, Saved, Needs attention) with the spec's state as a muted detail line. Shipped has Remove and no Undo; a cancelled file gets Retry and reads Needs attention in warn-fg where the spec shows it muted.
- CONTRACT.md says staff screens name files "Photo 1", never the original file name. QueueRow prints item.file.name (components/nabalens/upload-dialog.tsx:355) and uses it in every button label.
- No in-app camera is shipped. The whole Camera spec (dark screen, top bar with Close and Flip, labelled shutter, angle list, prompt plate, "Use N") has no code counterpart; the app hands off to the phone camera through a capture file input (with a library input beside it), which the spec treats only as the access-denied fallback.
- Dark stage rule: the spec says camera and viewer switch to the dark token set (data-theme="dark"). Shipped keeps the page theme and paints only the stage with --stage plus fixed --on-viewer colours; the guide viewer paints its whole dialog this way. The stage colour itself matches.
- Avatar sizes nearly line up: shipped sm is 36px, md 44px (the default) and lg 84px, as in the spec, but sm initials are 17px (the spec's 15px is under the type floor) and there is no xl of 112px/40px. Default hue fallback is 200 in the spec and 250 in code, and code hashes the hue from the name rather than storing one per person.
- Chips on photos: the spec puts the real state chip (shape, 32px, light outline values for Ready and Submitted) on the plate, with a 15px caption and a top-right video tag. Shipped TileBadge is one plain 28px square tag for every case, video badge bottom right, no 15px caption. Skeleton also lacks the spec's short line, 4:3 photo block, 52px button block and card wrapper, and its status line is visually hidden where the spec shows it.
- The spec has no wide-screen rule for the Photos grid: .ph-grid is 3 columns with a 4px gap at every width (cr:521-522); .grid4 (4 columns, 16px) is a separate general class, not a breakpoint of the photo grid.

### Differences to know: navigation and overlays

- Navigation model differs from the spec: the spec has a phone tab bar plus a left side nav from 1024px; the repo has a phone tab bar below 768px and a horizontal top bar of section links from 768px, with no side nav at any width (components/nabalens/app-shell.tsx:190-228, 281-312). The manager workspace adds a tab row under its header from 768px (components/nabalens/manager/manager-shell.tsx:92-94).
- Phone tab items differ: spec is Home, Photos, Add, (Manage), Me; shipped staff bar is Home, Photos, Add, People, Me and never shows Manage, whose link exists only in the top bar from 768px. The count badge sits on Home (to-do count), not Manage. Managers have a separate workspace bar: Overview, Review, Menu, Amenities with no Add.
- The shipped top bar carries only the wordmark, section links (from 768px) and account controls. Back, page title and venue scope, which the spec puts in the top bar, live in PageHeader and in feature-local back links; there is no shared Back component.
- Sheet and Dialog are one shipped component (components/ui/dialog.tsx) that switches at 768px. The spec's centred 358px phone confirm does not exist: every dialog and alert dialog is a bottom sheet on phones. Shipped desktop widths are 560, 760 (wide), 440 (alert) and 320 (alert sm) against the spec's 560 default and free `w`.
- Safe area: the spec uses fixed bottom padding (tab bar 20px, dock 24px, sheet 28px) and no env() inset; the repo uses env(safe-area-inset-bottom) and a 64px tab (`--size-tabbar`) against the spec's 60px. The action dock sits above the tab bar in the repo; in the spec it replaces it.
- Not shipped as shared components: Drawer, Side nav, Key values, Step marker (both forms). Stat exists only as Tally (grey 8px tiles with a 21px number inside one white card) plus a local admin copy with a 46px number; neither matches the spec's white 12px card with a 40px number.
- Menu diff tags are built from StatusChip, so they use the body face rather than mono; the uncertain tag comes first, is a square warn outline with an icon and no '?' sign when above zero (a grey pill at zero), and the unchanged count is a chip rather than plain text.
- Icon sizes, roles, ARIA and item lists in the Spec column come from assets/ui.js and the screens-*.js builders (cited as ui:N or by file), because the two CSS files and common-room.md do not state them. `aria-modal` on shipped dialogs depends on Base UI and was not verified from repo code.
